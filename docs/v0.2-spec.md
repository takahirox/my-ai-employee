# Fleet v0.2 仕様 — reviewed patch vertical slice

本書は Fleet v0.2 の実装規約である。キーワード **MUST**、**MUST NOT**、**SHOULD**、**SHOULD NOT**、**MAY** は規範要件を示す。「推奨実装」は同じ外部契約を満たす限り交換可能な設計選択である。

## 1. Executive recommendation

v0.2 は単一マシン向けの一つの縦切り機能に集中する。利用者が既存 Git repository で `fleet work "<goal>"` を実行すると、Fleet は sibling worktree を作り、任意導入の CLI 型 AI worker に計画と操作案を生成させ、すべての process・download・install を決定論的 policy と approval の下で実行し、project verification と evidence/review を経て reviewed patch を作る。元 workspace への反映は `fleet promote` を明示実行したときだけ行う。

既存の `DeterministicRuntime` を唯一の状態遷移・契約受理権限として維持し、その外側ではなく、その typed handler 境界に制御 service を追加する。worker は実行主体ではなく proposal generator である。v0.2 は direct vendor API、container、daemon、cloud control plane を必須にしない。offline demo、worker なし replay と「Deterministic Core, Probabilistic Intelligence」を保持する。

## 2. Evidence-based v0.1 gap analysis

### 保持して拡張する基盤

- `src/ai_employee/runtime.py` の `DeterministicRuntime` は graph revision/generation fence、contract、artifact/evidence、budget、pause/cancel/resume、completion gate を一元管理する。v0.2 でも authority root でなければならない。
- `src/ai_employee/runtime.py` の immutable `NodeProposal` と `src/ai_employee/graph.py` の graph acceptance は、「知能が候補を作り core が受理する」境界を既に持つ。
- `src/ai_employee/domain/policy.py` は built-in safety floor と制限方向だけの合成、stable failure を持つ。これを `PolicyResolver` の基礎にする。
- `src/ai_employee/domain/models.py` は strict/versioned Graph、Profile、Artifact、Evidence、Review、MergeDecision を持つ。unknown field rejection と digest-bound revision を保持する。
- `src/ai_employee/storage.py` の SQLite schema v1 は record、event、checkpoint、control、routing/metrics を永続化し、`src/ai_employee/inspector.py` は read-only projection を提供する。
- `src/ai_employee/cli.py` の `demo/run/inspect/replay/resume/pause/cancel/compare/serve/project` と `src/ai_employee/demo.py` の offline demonstration は互換対象である。
- `docs/architecture.md` が明記する通り、v0.1 の process-like node は構造化済み結果を受け取るだけで general subprocess API はなく、network/unrestricted process は safety floor で無効である。

### v0.2 で埋める不足

v0.1 には OS process 実行、network/download、dependency install、実 worker adapter、worktree lifecycle、human approval mailbox、patch review/promotion がない。Project Harness v1 (`docs/project-harness.md`) は commands/rules/protected paths を表すが、各権限と budget を実行可能な型として十分に表さない。Inspector は新しい request→decision→artifact の因果鎖をまだ表示しない。したがって core の書き換えでなく、immutable request と digest を介する controlled service 群の追加が必要である。

## 3. v0.2 product goal and measurable success criteria

**目標:** 信頼できない worker の提案から、隔離され、再現可能で、検証・レビュー済みの patch を安全に作り、利用者だけが元 workspace への反映を決定できること。

v0.2 release は以下をすべて満たさなければならない。

1. clean な fixture repository で一つの `fleet work` run が real CLI worker の小変更を sibling worktree 内だけに作る。
2. process/network/install request の 100% に canonical request digest、effective policy decision、実行結果または拒否、artifact provenance がある。
3. verification 必須項目と blocking review が未解決なら completion/promotion は不可能である。
4. `cancel` 後、対象 process tree が grace period + kill period 内に消滅し、run は再開可能または terminal cancelled のどちらかに決定論的に定まる。
5. worker を利用せず永続 event から同じ control-flow outcome と digest を replay できる。
6. promote 前の元 worktree は byte-for-byte/Git status 上不変であり、明示 promote 後だけ reviewed patch と一致する。
7. 既存 v1 Graph/Profile/SQLite reader、CLI demo/run/replay/inspect の互換試験が通る。

品質目標は、同一入力・policy・approval record・artifact set に対する policy/completion/replay digest の一致率 100%、すべての request の event coverage 100%、secret 値の log/artifact 流出 0 件である。worker 出力自体の同一性は要求しない。

## 4. Prioritized user journeys

### P0: reviewed patch を作る

利用者は `fleet work "入力検証を追加"` を実行する。Fleet は profile/policy/worker を解決し、隔離 workspace を用意し、worker proposal を plan として表示する。許可済み操作は進み、承認が必要な操作では `waiting_approval` になる。verification と review を通過した run は `ready_to_promote` になり、利用者が diff/evidence を確認して `fleet promote <run-id>` する。

### P0: 観察・制御する

別 terminal から `fleet logs --follow`、`fleet diff`、`fleet inspect`、`fleet approvals list/approve/deny`、`fleet cancel` を利用できる。cancel/restart 後は `fleet resume` が persisted checkpoint から安全に続行する。

### P1: plan-only と offline replay

`fleet work --plan-only` は worker が必要な場合も proposal の正規化・policy preflight までで、workspace mutation/process/network/install を一切行わない。`fleet replay` は worker、network、subprocess を起動せず、監査と不具合再現に使える。

### P1: worker を選ぶ

既定推奨は Codex CLI adapter、次点は Claude Code CLI adapter である。利用者は Harness または `--worker` で選ぶが、policy により候補を狭めるだけで権限は増えない。worker 未導入時は明確な availability failure または保存済み run の replay を得る。

## 5. Scope and explicit non-goals

### v0.2 scope

- local Git repository、一 run 一 sibling worktree、一つの明示 promotion。
- `PolicyResolver`、`WorkspaceManager`、`ProcessExecutor`、`DownloadClient`、`Installer`、`WorkerAdapter`、`ArtifactStore`、`ApprovalService`。
- Python project-local venv と Node project-local dependency の限定 install。
- HTTPS download と registry access の mediation、structured process execution、CLI worker 二種。
- deterministic verification、evidence/review gate、SQLite persistence、Inspector/replay。

### 明示的 non-goals

v0.2 は container を必須にせず、Fleet 自身の distribution/auto-update、任意 browser automation、raw/arbitrary socket、plugin marketplace、deployment、automatic merge/push/publish、credential discovery、host/global install、多数の package ecosystem、複数 host、Runtime の自己修正を実装しない。worker に shell/network credential を丸ごと渡す機能も作らない。これらを「実験的 bypass」として隠れて入れてはならない。

## 6. Architecture delta and control flow

### 権限境界

`DeterministicRuntime` は run/node state、accepted proposal、result contract、evidence gate、completion の唯一の writer であり続ける。各 service は capability-limited handler として request を受け、結果を返すだけで Runtime state を直接変更してはならない。CLI/worker/service は SQLite の domain record を直接更新してはならない。

制御 flow は次の通りである。

1. CLI が goal、repository identity、Harness、operator policy、run override を読み、run を作る。
2. `PolicyResolver` が immutable effective policy と digest を作る。
3. `WorkspaceManager` が clean/dirty 状態、HEAD、submodule を記録し、sibling worktree を作る。
4. `WorkerAdapter` が goal と bounded context から normalized plan/action proposal を返す。
5. Runtime が schema/contract/budget を検証し accepted graph revision に固定する。
6. action ごとに service が canonical request を policy resolve し、deny / approval_required / allow を返す。承認後も request digest と current policy を再検証する。
7. 実行結果、stdout/stderr、download/install、diff、verification を `ArtifactStore` に格納し、event から参照する。
8. deterministic verification と normalized review findings が completion gate を満たすと `ready_to_promote` になる。
9. `WorkspaceManager.promote` が元 workspace の基準 identity を再検証し、reviewed patch digest と一致する patch だけを適用する。

推奨実装は in-process service composition である。将来別 process 化しても request/result/event 契約は変えない。service 呼出しの順序は `request_recorded → policy_decided → approval_* → execution_started → execution_finished → artifact_recorded` とし、各 event は前 event digest を含む。

## 7. Data models and public interfaces

すべての public request/result は frozen strict model、`schema_version`、stable ID、`run_id`、時刻、canonical JSON SHA-256 digest を持つ。digest は secret の生値や非決定的時刻を対象 payload に含めず、canonical UTF-8、sorted key、明示 null 規則で計算する。unknown field/version は fail closed とする。ID は同一性、digest は内容同一性であり代用しない。

中心 model は以下である。

- `ActionProposal`: worker、kind (`process|download|install|edit_intent|review`)、typed payload、理由、期待 artifact、proposal digest。実行能力を持たない。
- `PolicyDecision`: request digest、effective policy digest、`allow|deny|approval_required`、stable reason code、limits、required approval classes。
- `ApprovalRecord`: approval ID、request/policy digest、scope、decision、operator identity label、created/expires/decided time。秘密や OS user credential は保存しない。
- `ArtifactDescriptor`: content digest、media type、size、logical kind、producer action、source/provenance、redaction state、store locator。
- `ExecutionResult`: request digest、status、stable failure、exit code、timing、resource usage、stdout/stderr artifact refs。
- `WorkspaceSnapshot`: repository realpath identity、original worktree path、HEAD/base tree、dirty-state digest、isolated path、worktree metadata。
- `PromotionRecord`: base identity、reviewed patch digest、verification/review digest、preflight result、applied tree/diff digest。
- `AcceptanceLedger`: completion criterion ごとの disposition と evidence refs を保持する。同一の検証済み artifact/path/command result が複数 criterion を満たす one-to-many 関係を許容しなければならず、criterion ごとに内容が同じ証拠の複製を要求してはならない。Runtime は evidence ref の source version/digest と criterion の要求を個別に検証する。

public interface の最小契約を次に示す（言語上の署名は非規範）。

```text
PolicyResolver.resolve(request, policy_layers) -> PolicyDecision
WorkspaceManager.create(run, repository) -> WorkspaceSnapshot
WorkspaceManager.capture_diff(snapshot) -> ArtifactDescriptor
WorkspaceManager.promote(snapshot, reviewed_patch, approval) -> PromotionRecord
ProcessExecutor.execute(ProcessRequest, decision, cancellation) -> ExecutionResult
DownloadClient.fetch(DownloadRequest, decision, cancellation) -> DownloadResult
Installer.install(InstallRequest, decision, cancellation) -> InstallResult
WorkerAdapter.probe() -> WorkerAvailability
WorkerAdapter.propose(WorkerRequest, mediated_channel) -> WorkerResult
ArtifactStore.put(stream, metadata) -> ArtifactDescriptor
ArtifactStore.open_verified(descriptor) -> stream
ApprovalService.request(decision) -> ApprovalRecord
ApprovalService.decide(id, request_digest, decision) -> ApprovalRecord
```

すべての service は request digest の不一致、期限切れ approval、取消を副作用前に拒否しなければならない。同じ idempotency key の completed request は同じ result ref を返し、in-progress/unknown outcome は重複実行せず `indeterminate` とする。

stable failure は少なくとも `POLICY_DENIED`、`APPROVAL_REQUIRED`、`APPROVAL_EXPIRED`、`INVALID_REQUEST`、`BUDGET_EXCEEDED`、`TIMEOUT`、`CANCELLED`、`SPAWN_FAILED`、`PROCESS_FAILED`、`NETWORK_BLOCKED`、`DNS_REBIND_BLOCKED`、`TLS_FAILED`、`INTEGRITY_FAILED`、`INSTALL_DENIED`、`WORKER_UNAVAILABLE`、`WORKER_PROTOCOL_ERROR`、`VERIFICATION_FAILED`、`REVIEW_BLOCKED`、`WORKSPACE_CONFLICT`、`PROMOTION_FAILED` を含む。message は診断用であり制御判定に使わない。

## 8. Process execution contract

`ProcessRequest` は `argv: non-empty list[string]`、workspace-relative `cwd`、filtered environment の key/value または allowlisted inheritance、stdin artifact ref、timeout、expected exit codes、output limits、process budget class、purpose を型付けする。既定では shell string、`shell=true`、PATH lookup が曖昧な executable、worktree 外 cwd を禁止する。shell が project command として明示許可される場合も approval-required class とし、shell executable と script artifact を固定する。

`cwd` は symlink 解決後も isolated worktree または明示された Fleet state directory 内でなければならない。environment は空の基底から `PATH` 等の operator allowlist と request allowlist を合成し、credential-like key (`*TOKEN*`, `*SECRET*`, `*PASSWORD*`, cloud/vendor auth 等) は明示 secret binding なしに継承しない。値は log/digest 表示時に redact する。worker probe のための既存認証は CLI 自身が管理してよいが、Fleet は値を読まない。

stdout/stderr は bounded stream として別 artifact に保存し、terminal には redaction 済み tail を表示する。byte limit 超過時は artifact を truncate marker 付きで閉じ、policy に従い process を失敗または継続させる。exit code、signal、開始/終了 monotonic duration、timeout/cancel reason を result に残す。

timeout/cancel 時は新しい process group/session 全体に soft termination を送り、`termination_grace_seconds` 後に hard kill し、`kill_grace_seconds` 後に残存確認する。子孫を追跡できない platform では executor availability を拒否するか、同等の job object/cgroup 機構を使う。Fleet 自身の取消状態を先に terminal にせず cleanup outcome を event 化する。

budget は run/action ごとに process count、concurrency、wall time、CPU（取得可能時）、stdout/stderr bytes を上限化する。policy limit を超える request は spawn 前に拒否し、実行中超過は取消と同じ cleanup を行う。再試行は request に明示された deterministic retry policy のみで、non-idempotent process は自動再試行しない。

## 9. Network/download contract

network mode は `disabled`、`restricted`、`full` の三つである。既定および built-in floor は `disabled`。`full` は「無検査」ではなく operator machine policy が許可し、action 単位 approval を得た場合だけ使え、TLS/size/time/provenance/secret 規則は残る。worker proposal や project profile だけで full に昇格できない。

`DownloadRequest` は HTTPS URL、purpose、expected media type、maximum bytes、timeout、optional SHA-256、destination artifact kind を持つ。restricted mode は `https` のみ、domain の exact/suffix allowlist、既定 port 443（追加 port は operator policy）、禁止 protocol を検査する。userinfo、fragment、IP literal、non-HTTPS downgrade は既定拒否とする。

各接続および redirect ごとに URL を再 parse し、scheme/domain/port allowlist を再評価し、DNS を解決する。loopback、link-local、private、carrier-grade NAT、multicast、unspecified、documentation/reserved range、および IPv4-mapped IPv6 を拒否する。接続先 IP が検査済み集合に属することを transport 層で固定し、redirect 上限を設けることで DNS rebinding/SSRF を防ぐ。proxy は operator policy で明示されたものだけを使い、proxy environment を暗黙継承しない。

system trust store による hostname/TLS certificate 検証を無効化してはならない。connect/read/total timeout、compressed/decompressed byte 上限、content-length early rejection を適用する。partial file は install に渡さない。checksum 指定時は一致必須、未指定時も実 content digest、final URL、redirect chain、resolved peer、TLS summary（秘密を除く）、取得時刻、request/policy digest を provenance に残す。

Authorization/Cookie/client certificate は explicit secret binding と domain scope がある場合だけ添付し、redirect 先に転送しない。header/body/log の secret は redact し、worker に credential 値を返さない。一般 HTTP client や socket handle を worker に公開しない。

## 10. Dependency installation contract

v0.2 Installer は `python_venv` と `node_project` のみを扱う。常に isolated worktree 内の project-local target を使い、sudo、system prefix、global/user-site、`npm -g`、host package manager を `HOST_INSTALL_DENIED` として拒否する。

`InstallRequest` は ecosystem、operation class、manifest/lock paths と preimage digest、package manager executable/version、argv、target、network need、lifecycle-script policy、expected mutations を持つ。operation class は次を区別する。

1. `existing_lock`: committed manifest/lock と一致する再現 install。許可候補。
2. `new_dependency`: package 名/version の追加。approval 必須。
3. `manifest_lock_mutation`: manifest または lockfile 変更。approval 必須で、変更 artifact を review 対象にする。
4. `lifecycle_scripts`: install hook/build script 実行。既定拒否、operator が package/scope を許可したときも approval 必須。
5. `new_registry_domain`: allowlist 外 registry/domain。network と install の双方の approval 必須。
6. `host_global`: v0.2 では常に拒否し override 不可。

Python は worktree 内 `.venv`（または Harness の local path）を作り、lock/requirements の hash pin を優先する。Node は worktree 内 `node_modules` と project lock を使い、既存 lock install は frozen/immutable mode を要求する。package manager cache は Fleet 管理 directory に置けるが、cache hit も provenance と content digest を検証し、別 run の権限を継承しない。

download は必ず `DownloadClient` と同等の policy path を通す。package manager が内部通信を隠して mediation できない場合、restricted proxy/registry mirror または pre-fetched offline cache を用い、どちらも利用不能なら fail closed とする。install 前後の manifest、lockfile、target file inventory digest、executed scripts、package manager output、registry provenance を artifact 化する。inferred dependency command は提案にすぎず permission ではない。

## 11. Worker adapter strategy

最初の推奨 adapter は Codex CLI、第二の任意 adapter は Claude Code CLI であり、direct vendor API は要求しない。両者は同じ `WorkerAdapter` 契約に normalize し、Runtime/PolicyResolver が vendor 固有 output を解釈してはならない。

### Task-aware routing

組み込みの cloud-only operator fallback は `codex-balanced` を提供し、operator
machine policy はこれを strategy の正確な ID/backend/model/effort/capabilities/bounds
ごと置換できる。Project Harness は ID/backend を狭めるだけで、adaptive/local を
明示的に opt in しなければならない。候補はまず authority、required capability、
risk の制約を満たさなければならず、その後で complexity/scale に対する最小十分な
fit を選ぶ。
mature history は同等 fit の候補間でのみ adaptive selection に使ってよい。

operator は既存 strategy ID の名前付き集合を strategy set として定義してよい。
`--strategy-set` は routing 起動時の候補をその集合へ限定し、set 自体が model/effort
を再定義してはならない。set 名は assessment/selected strategy とともに Inspector
へ永続化し、Codex-only、Claude-only、mixed、Local-only の比較条件を再現可能にする。
operator は `default_strategy_set` を1つ指定してよい。`fleet work` の既定 routing
mode は adaptive で、CLIでsetが省略された場合にdefault setを使う。CLIの明示setは
defaultより優先する。従来のworker/model直接指定は`--routing-mode legacy`で明示する。
strategy setは自身のassessment strategy IDを指定してよく、CLI明示assessor、set固有
assessor、global default assessorの順で解決する。組み込み`claude-only`は評価を
`claude-fable-5`/`high`、通常・低risk実行を`claude-opus-5`/`high`、Opus bounds外を
`claude-fable-5`/`high`とし、CodexまたはLocalへfallbackしてはならない。

adaptive mode は execution strategy 選択前に、operator が指定した正確な assessment
strategy でrepository-isolated strict-JSON semantic assessmentを1回行う。組み込み既定は
`codex-sol-high` (`gpt-5.6-sol` / `high`) とし、CLIの
`--assessment-strategy` はHarnessで許可された正確なstrategy IDだけを選べる。
assessment subprocessもProcess/Artifact/Policy境界を通し、空のread-only workspaceを
使う。Local assessorはProject Harnessのlocal opt-inなしに使ってはならない。

assessment protocol v2の出力は、strictかつfrozenなcategorical profileだけとする。
task typeは`mechanical/retrieval/diagnosis/implementation/architecture/research/planning/
open_ended_strategy`、reasoning classは`mechanical/simple/moderate/deep/open_ended`、
scopeは`bounded/local/multi_component/broad`、ambiguityは`low/medium/high`とし、1件から
10件の非空reasonを必須にする。risk、capability、strategy ID、model、effort、cost、
policy/routing decisionを出力してはならない。goalはuntrusted dataとして扱い、toolを
使用せず、unknown field/enum、malformed output、worker failureは別assessment modelや
execution modelへfallbackせずfail closedとする。旧v1 numeric assessment parserは
互換性のためimport可能なまま維持するが、新adaptive pathでは使用しない。

互換numeric complexityはtask typeの`1/2/4/3/7/6/4/9`、reasoning classの
`1/2/4/7/9`、ambiguityの`1/4/7`の最大値とする。scaleはscopeを
`bounded=1/local=2/multi_component=5/broad=8`へ写像する。表は網羅的であり、model由来
numeric scoreやhidden weightを持たない。新しい決定的assessmentはprofile統合前に
`complexity=1/scale=1`を使い、正規化goal長を`context_character_count`として永続化する。
このcount、構造segment数、capability数はeligibility、floor、headroom、tie-breakに
使用しない。Harness由来riskとcaller/node risk、effective/required capabilityは独立した
hard factとして変更しない。

新adaptive planner protocol v2は各nodeにprofileを必須とし、受理前にnumeric fieldsを
決定的写像値で上書きする。profile欠落nodeはfail closedとする。旧profile-less graphは
fixed/policy、hand-authored、replay互換のためstored numeric fieldsを維持する。各nodeの
profileは既存`NodeRouteRecord.assessment`へコピーし、route digest、execution/evaluator/
failure fact、Inspectorの既存projectionをそのまま再利用する。

fixed mode は指定された正確な ID を選ばなければならない。適格候補がなければ別の
model/backend/local へ fallback せず fail closed とする。assessment と selection は
永続化し、decomposition は top-level assessment data としてのみ扱い、独立 subtask
として実行してはならない。legacy `--worker` 動作は明示modeとして維持し、
exact model/effort は Codex CLI の model/config、Claude Code CLI の model/effort、
Ollama CLI の model/think 引数へ bind する。Local は operator set の選択に加えて
Project Harness の `local_backend` opt-in がなければ fail closed とする。

`probe()` は executable の存在、adapter-supported version、非対話利用可否、認証の有無を「available/unavailable/unknown」として返す。probe は model request を発行せず model token を消費してはならない。Fleet は credential file/env の内容を読まず、CLI が提供する status/version の secret-free result のみを記録する。安全な non-token auth status が vendor CLI にない場合は `auth_unknown` とし、試験 request を送らない。

`propose()` の入力は goal、accepted plan/revision、workspace-relative bounded file context、Harness、effective capabilities、remaining budgets、prior structured results である。出力は versioned envelope の plan/action proposals、assistant note、usage summary であり、自由文中の tool command を実行してはならない。adapter は vendor tool use を無効化するか、すべての tool callback を Fleet mediated channel に変換する。worker subprocess 自体も `ProcessExecutor` の worker class policy、timeout、output budget、cancellation の対象である。

malformed/unknown proposal は `WORKER_PROTOCOL_ERROR`。adapter は output normalization と vendor error mapping のみを担当し、policy allow、approval、completion を決めない。session resume token を保存する場合は opaque secret artifact として暗号化/permission 制限し、Inspector に表示しない。v0.2 の推奨単純実装は各 planning turn を bounded subprocess とし、worker が session resume を提供しなくても run checkpoint を再構成できる方式である。

## 12. Workspace, verification, review, approval, and promotion flow

### Workspace

入力は Git worktree でなければならない。Fleet は repository common-dir、元 worktree realpath、HEAD commit/tree、index、tracked/untracked/ignored dirty summary を記録する。既定では dirty 元 workspace を拒否する。operator が明示許可する場合も dirty patch/untracked inventory digest を baseline とし、それらを isolated worktree や promotion に暗黙混入させない。

isolated workspace は repository 内でなく Fleet state root 配下の sibling directory に `git worktree add --detach <base-commit>` で作る。path traversal/symlink escape を拒否し、run が所有する path だけを cleanup する。submodule/LFS が必要なら Harness で明示し、それぞれ download policy を通す。元 worktree は promotion まで read-only logical boundary である。

### Verification と review

Harness の required verification command は typed `ProcessRequest` に変換し、同じ executor/policy を通る。各結果は command digest、exit、output artifact、対象 tree/diff digest を持つ。required check が一つでも missing/failed/stale なら completion を拒否する。worker の「成功した」という文は evidence にならない。

review input は base、review candidate diff、verification evidence、policy exceptions、approval records、generated artifacts で固定する。deterministic checks（protected path、size、binary、secret scan、unexpected manifest mutation）を先に実施し、任意 AI reviewer の findings は normalized severity/scope/code/path にする。critical/high および essential medium は blocking。review 後に diff が変われば review/verification は stale となり再実行する。

### Approval

approval scope は一 request digest を既定とする。batch approval は同一 action class、明示列挙した digest、短い expiry に限定する。`approve`/`deny` は operator に reason、risk、argv/domain/package、limits、diff impact を提示し、actor label と時刻を記録する。approval は policy deny を allow に変えず、`approval_required` を limits 内で allow にするだけである。非対話 mode は auto-approve せず `waiting_approval` と stable exit を返す。deny/expiry/policy change 後の再提案は新 digest/new approval とする。

### Promotion

promotion は別の明示 action であり、自動実行しない。必要条件は `ready_to_promote`、未期限切れ promotion approval、reviewed patch digest 一致、全 required evidence、blocking finding なしである。開始直前に元 repository common-dir、HEAD、index、dirty-state baseline を再検証し、変化があれば `WORKSPACE_CONFLICT` で何も適用しない。

patch は `git apply --check` 相当の preflight 後、元 worktree に一回だけ適用する。v0.2 は commit、merge、push、publish を行わない。途中失敗時は可能なら適用前 snapshot へ戻すが、ユーザー既存変更を消す destructive reset は禁止する。原子的 rollback を保証できない platform 状況では promotion 前に拒否する。成功後は resulting diff/tree digest を照合し `PromotionRecord` を保存する。同一 promotion idempotency key の再実行は no-op success、それ以外の二重適用は拒否する。

## 13. Project Harness v2 and policy precedence, with concise YAML

Harness v2 は repository-owned explicit policy intent であり、OS sandbox や machine policy の代替ではない。簡潔な例を示す。

```yaml
schema_version: 2
commands:
  test: {argv: [".venv/bin/python", "-m", "pytest", "-q"], cwd: "."}
  lint: {argv: [".venv/bin/python", "-m", "ruff", "check", "."], cwd: "."}
paths:
  writable: ["src/**", "tests/**", "pyproject.toml", "uv.lock"]
  protected: [".git/**", ".fleet/policy.yaml", "secrets/**"]
verification:
  required: [test, lint]
  review: {required: true, block_severities: [critical, high]}
network:
  mode: restricted
  https_domains: ["pypi.org", "files.pythonhosted.org"]
  ports: [443]
install:
  ecosystems: [python_venv]
  existing_lock: allow
  new_dependency: approval
  lifecycle_scripts: deny
approvals:
  process_shell: required
  new_dependency: required
  promotion: required
worker:
  preferred: codex_cli
  allowed: [codex_cli, claude_code_cli]
budgets:
  wall_seconds: 1800
  worker_turns: 12
  processes: 40
  download_bytes: 50000000
  artifact_bytes: 100000000
```

commands は名前付き argv/cwd/env allowlist、paths は workspace-relative glob、verification は required command と evidence freshness、network/install/approvals/worker/budgets は上記 contract の型を使う。相互参照のない command、absolute/escaping path、重複 key、unknown field/version、矛盾する allow/protected path は stable validation error とする。inference は provisional suggestion を作れるが、explicit Harness として保存・承認されるまで process/network/install permission を一切付与しない。

precedence は強い順に **built-in runtime floor > operator machine policy > explicit project policy > run override > worker proposal** である。合成は集合の intersection、boolean deny 優先、数値 minimum、approval requirement の union とする。下位 layer は allowlist を狭め、deny/approval を追加し、limit を下げられるだけである。省略は上位値を継承し、`allow` として扱わない。layer と effective policy は canonical artifact/digest を持つ。run 中に machine/project policy digest が変われば未実行 request を再 resolve し、権限増加は新 run/明示確認、制限強化は即時適用する。

## 14. CLI UX and exit/status behavior, with examples

primary UX と関連 command は次の通りである。

```console
$ fleet work "入力検証とテストを追加"
run_01...  waiting_approval  fleet approvals show run_01...
$ fleet work --plan-only --worker codex-cli "依存更新案を作る"
$ fleet approvals list --run run_01...
$ fleet approvals approve apr_01... --request-digest sha256:...
$ fleet logs run_01... --follow
$ fleet diff run_01... --stat
$ fleet diff run_01... --artifact reviewed.patch
$ fleet inspect run_01...
$ fleet cancel run_01...
$ fleet resume run_01...
$ fleet promote run_01... --patch-digest sha256:...
```

`work` は `--repo`、`--profile`、`--worker`、`--plan-only`、制限方向だけの `--budget-*`/`--network=disabled|restricted`、`--non-interactive`、`--json` を受ける。goal は argv 一要素として扱い shell 展開しない。plan-only は state を `planned` で止め action preflight を表示する。`logs` は event cursor で再開可能、`diff` は isolated workspace を読むだけ、`inspect` は provenance graph と status を読むだけである。

run status は少なくとも `planning`、`planned`、`running`、`waiting_approval`、`verifying`、`reviewing`、`ready_to_promote`、`promoting`、`completed`、`paused`、`cancelled`、`failed` を持つ。`completed` は promotion 成功後を意味し、patch 作成だけなら `ready_to_promote` である。cancel request は `cancelling` event を出し cleanup 後に terminal 化する。resume は last durable checkpoint、accepted revision、generation、policy digest、完了 action idempotency を検査する。

process exit status は `0=要求した同期操作の成功`、`2=CLI/validation error`、`3=policy denied`、`4=approval待ち`、`5=verification/review blocked`、`6=worker unavailable/protocol failure`、`7=cancelled`、`8=workspace/promotion conflict`、`9=internal/storage failure` とする。非 terminal run を正常に作成した async 表示は 0 でよいが、`--non-interactive` が承認で停止した場合は 4。JSON output は schema version、run/status、stable code、next actions を持ち、人間向け message の parse を要求しない。

既存 `fleet demo/run/inspect/replay/resume/pause/cancel/compare/serve/project` は残す。引数/出力 schema を破壊的変更せず、新しい `inspect/resume/cancel` は legacy run と v0.2 run を discriminator で扱う。

## 15. Events, artifacts, metrics, storage, replay, and Inspector

process、network、install、worker、approval、workspace、verification、review、promotion の **request・decision・開始・終了/拒否** はすべて event を出す。event は schema version、event/run/action ID、sequence、timestamp、kind、actor class、request/result/policy/artifact digests、previous event digest を持つ。秘密値と巨大 body は event に inline せず artifact ref にする。

`ArtifactStore` は content-addressed、write-once で、temporary file に stream → size/hash 検証 → atomic rename を行う。metadata は producer、request/policy/worker/version、source URL/package、base/candidate tree、redaction、media type、creation time を含む。DB は locator と digest を持ち、読出し時に digest を再検証する。stdout/stderr、worker envelope、download、install inventory、diff/patch、verification、review、policy、approval/promotion record を保存する。retention/GC は terminal run と promotion record の参照を壊してはならない。

SQLite は schema version を明示し、migration は transaction、backup/rollback、forward-version refusal を持つ。event append と domain checkpoint は可能な限り一 transaction にし、artifact publish 後 DB commit が失敗した orphan は安全な GC 対象にする。single-machine writer lock と busy timeout を定義し、同一 run の並行 controller writer を lease/generation fence で拒否する。

metrics は request count、allow/deny/approval、approval latency、worker turns/duration/declared usage、process duration/exit、download bytes/cache、install class、verification/review outcome、artifact bytes、cancel cleanup、time-to-ready/promote を action/run/adapter 単位で持つ。goal/source/stdout/secret/domain の高 cardinality 生値を label にしない。cost は vendor が返した値のみ provenance 付きで記録し、推測値と区別する。

replay は accepted proposal、policy decision、approval、result envelope、event ordering を読み、worker/process/network/install/Git mutation を行わず Runtime transitions と completion digest を再計算する。artifact 不足/破損、schema 非対応、digest mismatch を明示し、live action で補完しない。

Inspector は read-only で timeline、request→policy→approval→result、workspace/base/candidate/promoted diff、verification coverage、review findings、budgets、metrics、provenance、replay status を表示する。secret artifact は metadata/redaction marker のみ表示し、download link を提供しない。localhost bind を既定とし、既存 v1 projection を維持する。

## 16. Security threat model and mitigations

信頼境界上、worker output、repository file/Harness、package/registry、network response、process output はすべて不信であり、operator machine policy と built-in floor のみが上位 authority である。

| 脅威 | 必須 mitigation |
|---|---|
| prompt injection が tool 実行を命令 | worker は proposal のみ。strict schema、Runtime acceptance、request ごとの policy/approval |
| command injection | argv 既定、shell 拒否、cwd/env/executable 固定、自由文を command に変換しない |
| path traversal/symlink race | realpath containment、open-time revalidation、protected paths、worktree 分離 |
| credential theft/log leakage | credential discovery 禁止、env deny/filter、explicit binding、redaction、secret artifact 非表示 |
| SSRF/DNS rebinding/redirect escape | HTTPS allowlist、各 hop 再検証、private range 拒否、検査済み IP pin、proxy 規則 |
| supply-chain compromise | lock/hash、TLS、provenance、registry allowlist、lifecycle script deny/approval、local install |
| malicious/large output | stream byte/time limit、content digest、safe rendering、binary/HTML 非実行 |
| child process escape/DoS | process group cleanup、count/time/output budgets、no host/global install |
| approval confusion/replay | exact request+policy digest、expiry、actor/audit、変更後の再承認 |
| TOCTOU promotion | base/index/dirty/diff digest 再検証、apply preflight、idempotency、no auto merge/push |
| DB/artifact tampering | append ordering、digest verification、schema/version fence、read-only Inspector |
| worker/vendor compromise | least context/capabilities、adapter normalization、token-free probe、vendor tool bypass 禁止 |

OS-level sandbox が利用可能なら defense-in-depth として SHOULD 使用するが、v0.2 portability のため container を必須にしない。sandbox 不在を理由に policy mediation を省略してはならない。protected file や network enforcement を対象 platform で保証できない capability は availability check で fail closed とする。

## 17. End-to-end acceptance scenario and Definition of Done

repository に disposable fixture（製品 source とは分離）を用意する。小さな Python または Node project、deterministic failing test、Harness v2、lockfile、許可済み registry、禁止 action を含める。real worker credential は CI secret として要求せず、operator が既に認証済み CLI を持つ opt-in acceptance job で実施する。

1. fixture を temporary Git repository として初期化し base tree/status digest を記録する。
2. `fleet work` で「小関数を実装しテストを通す」を Codex CLI（同 contract の Claude adapter test も別途）に依頼する。
3. worker が小 code/test change を提案し、Fleet が sibling worktree だけに編集を反映する。
4. controlled dev dependency の download/install を要求する。既存 lock install は restricted HTTPS/provenance の下で実行し、新 dependency または lifecycle script は approval 待ちにする。
5. 少なくとも一つの host/global install、private-IP download、protected-path edit のいずれかを deterministic deny し、run が bypass しないことを示す。
6. approval digest を指定して approve/deny し、wrong/stale digest が拒否されることを示す。
7. long-lived child を起動する fixture action を cancel し、parent/child 消滅、cleanup event、durable cancelled/checkpoint を確認する。再開可能 branch は resume して二重実行がないことを確認する。
8. deterministic tests を通し、diff/outputs/provenance を evidence にし、review gate 後 `ready_to_promote` にする。evidence を一つ除いた clone/replay は completion を拒否する。
   同じ仕様書や test report が複数の completion criterion を満たす fixture では、共有 evidence ref を各 criterion に関連付け、一つの artifact しかないことを理由に再試行または偽失敗してはならない。
9. Fleet/worker/network を無効にして SQLite + artifact copy を replay し、transition/completion digest 一致を確認する。
10. promote 前に元 status/tree が base と一致することを確認し、wrong digest と変更済み base の promotion を拒否する。正しい digest を明示 promote し、expected patch のみ適用され commit/push されないことを確認する。

Definition of Done は、この scenario が対応 platform gate で再現可能、全 request event coverage 100%、secret scan clean、cleanup に残存 process なし、worker なし replay 一致、legacy compatibility green、文書化された stable exit/failure を満たすことである。real worker の確率的 text/diff 完全一致は gate にせず、small-change contract、policy/evidence outcome を gate にする。

## 18. Test strategy

- **Unit:** canonicalization/digest、strict model/version、policy precedence/monotonicity、argv/env/cwd、URL/redirect/DNS/IP/TLS、install classification、approval expiry/digest、stable failure、budget math。
- **Property/fuzz:** 下位 policy が権限を増やさないこと、URL parser/private ranges、path containment/symlink、malformed worker envelope、canonical JSON の順序不変性。
- **Service integration:** fake executable/process tree、local TLS test server と DNS resolver、fake registry/package、artifact crash points、SQLite migration/locking。外部 network を使わない。
- **Adapter contract:** recorded secret-free Codex/Claude outputs と local fake CLI で probe が model call をせず、proposal normalization/cancel/error mapping が同じになることを検証する。
- **Runtime integration:** proposal→decision→approval→result→evidence gate、共有 evidence ref から複数 criterion への one-to-many acceptance、pause/cancel/resume、generation fence、stale result、idempotency、worker-free replay。
- **Git integration:** detached sibling worktree、dirty/untracked/submodule cases、base race、apply check、wrong patch digest、promotion failure/no commit/no push。
- **Security regression:** shell injection、env secret、redirect/private IP/rebinding、zip/package traversal、lifecycle hook、ANSI/HTML output、protected path、approval replay。
- **End-to-end:** 第17章の offline deterministic fixture を通常 CI、real worker slice を明示 opt-in release gate で行う。

platform ごとに process-tree cleanup と filesystem atomicity の contract test を必須とする。時間依存 test は injectable clock、network は local deterministic server、worker は fake/recorded adapter を通常 test に使う。real adapter test が unavailable の場合、release gate を「skip success」にせず理由付き未充足として扱う。

## 19. Migration and compatibility

Graph/Profile/domain record は各自の `schema_version` を維持する。Project Harness v1 reader は残し、v1 を読み込むと commands/rules/protected paths を v2 の provisional restricted representation に memory 上で変換する。欠ける network/install/approval は `disabled/deny/required` の安全側 default とし、変換は repository file を自動書換えしない。`fleet project --migrate --output ...` は review 用 v2 candidate を別 path/stdout に生成できる。

SQLite は v1 database を read/inspect/replay できなければならない。v2 write が必要な時だけ明示 transaction migration を行い、schema table と migration journal を更新する。migration failure は元 DB を利用可能に保ち、newer unknown version は read/write とも明確に拒否する。v1 event に存在しない provenance は `not_recorded_v1` と表示し捏造しない。

既存 Graph/Profile JSON/YAML、public model discriminator、`demo/run/inspect/replay/resume/pause/cancel/compare/serve/project` の意味を保持する。legacy `run` を暗黙に `work` に変換しない。v0.1 replay は新 worker/service を呼ばない。新 field は version 2 model のみに追加し、v1 strict parser を緩めない。

artifact/event migration は content を書換えず locator/index を追加する。digest algorithm/version を metadata に持たせ、将来 algorithm 変更時も既存 digest を検証可能にする。migration と rollback fixture を release gate に含める。

## 20. Phased implementation plan, critical path, and release gates

### Phase A — contracts and policy foundation

immutable request/result/event/artifact model、canonical digest、Harness v2 parser/migration、`PolicyResolver`、stable failures を実装する。gate は precedence/property test、unknown version fail-close、v1 compatibility。ここが全 service の critical path である。

### Phase B — artifact/process/workspace substrate

`ArtifactStore`、`ProcessExecutor`、cancellation/process-tree cleanup、`WorkspaceManager` create/diff/cleanup を実装する。gate は crash/idempotency、path/env/argv security、platform cleanup、元 workspace 不変性。

### Phase C — download and install

`DownloadClient` の restricted HTTPS 防御、Python/Node local `Installer`、provenance を実装する。gate は local adversarial network tests、install classification、lock/checksum、host/global hard deny。安全な mediation が不可能な package-manager mode は出荷しない。

### Phase D — worker and orchestration UX

normalized adapter contract、Codex CLI、任意 Claude Code CLI、token-free probe、`fleet work/plan/logs/diff/approvals/cancel/resume` を Runtime に接続する。gate は fake adapter full flow、real adapter opt-in、全 tool request mediation、budget/cancel。

### Phase E — evidence, review, promotion, observability

verification/review gate、explicit promote、events/metrics、Inspector/replay v2 を完成する。gate は stale evidence/diff rejection、base conflict、no auto commit/merge/push、第17章 acceptance、v1 migration/compatibility。

release candidate は security regression、supported platform cleanup、offline replay、DB migration、real worker acceptance をすべて通す。critical path は **model/policy → process/artifact/workspace → network/install → worker orchestration → evidence/review/promotion**。Inspector の装飾、追加 adapter、cache optimization は critical path ではなく、契約を遅らせるなら延期する。

## 21. Deferred v0.3+ work

以下は v0.3 以降に明示的に延期する: mandatory container sandbox、Fleet distribution/auto-update、arbitrary browser/socket、plugin marketplace、deployment provider、automatic merge/commit/push/publish、credential discovery/secret manager crawling、Python/Node 以外の多数 ecosystem、distributed/multi-host scheduler、remote approval service、Runtime self-modification。container や OS sandbox adapter を任意 defense-in-depth として試験することは MAY だが、v0.2 の正しさをそれだけに依存させない。

## 22. Final prioritized requirements using MUST / SHOULD / MAY

### P0 — MUST

1. `fleet work` は sibling Git worktree 内だけで worker proposal を実行し、元 workspace を明示 promote まで変更してはならない。
2. `DeterministicRuntime` は state/contract/evidence/completion の authority root であり、worker は immutable structured proposal を返すだけでなければならない。
3. すべての process/network/install/worker/approval/workspace/review/promotion action は typed request、canonical digest、deterministic policy decision、event、provenance artifact を持たなければならない。
4. policy は built-in floor > machine > project > run override > worker proposal の順で合成し、下位層は制限・承認・上限低下しかできてはならない。
5. process は argv を既定とし、cwd/env/output/timeout/cancel/process-tree/budget/stable failure を本書通り制御しなければならない。
6. network は disabled/restricted/full を持ち、full も operator-controlled approval gate、restricted は HTTPS/domain/protocol/port/redirect/DNS/private-range/TLS/size/time/checksum/provenance/proxy/secret 防御を必須とする。
7. install は Python venv/Node project-local に限定し、operation class を区別し、host/global を常に拒否しなければならない。
8. Codex CLI adapter を第一推奨として実装し、Claude Code CLI を同一 normalized contract の任意第二 adapter とする。probe は token を消費せず credential を露出してはならない。
9. Harness v2 は commands/paths/verification/network/install/approvals/worker/budgets を型付けし、inference を permission としてはならない。
10. required verification と review/evidence gate を満たした exact diff だけが `ready_to_promote` になり、promotion は digest/base を再検証する明示 action でなければならない。自動 commit/merge/push/publish をしてはならない。
11. SQLite persistence、cancel/resume、worker なし replay、Inspector provenance、v1 Graph/Profile/SQLite/CLI/demo/replay compatibility を維持しなければならない。
12. 第17章の disposable acceptance と第18章の security/compatibility gates を release 前に満たさなければならない。

### P1 — SHOULD

1. content-addressed ArtifactStore は atomic publish、deduplication、retention-safe reference、read verification を提供すべきである。
2. supported OS の sandbox を defense-in-depth として使い、process resource usage を取得可能な範囲で計測すべきである。
3. CLI は JSON schema output と actionable next command を提供し、Inspector は action provenance chain と evidence freshness を表示すべきである。
4. lock/hash pin、offline cache/mirror、recorded adapter fixture により通常 test を外部 service から独立させるべきである。
5. review は deterministic checks を AI review より先に行い、cost/latency を増やさず明白な violation を拒否すべきである。

### P2 — MAY

1. 同じ契約の追加 CLI worker adapter、任意 OS sandbox backend、承認済み batch approval を追加してよい。
2. provenance を保つ verified download/package cache、read-only richer Inspector visualization、policy simulation を追加してよい。
3. plan-only proposal を export/import してよいが、import 後も current policy、digest、approval を再評価しなければならない。

任意機能が P0 の authority boundary、fail-closed behavior、元 workspace 不変性、offline replay を弱める場合は実装してはならない。
